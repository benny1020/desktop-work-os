# Worklane assistant memory — upstream source review

Reviewed on **2026-10-04**. This is a source-backed design review, not a claim that Worklane runs these frameworks. We shallow-cloned the primary GitHub repositories, inspected the files below, and cross-checked official documentation. No upstream packages were installed, no upstream services were run, and no upstream implementation was copied into Worklane. Downloaded repositories stay ignored under `research/memory-upstream-*`.

## Recommendation

Build a small durable memory layer around Worklane’s existing Electron boundary. Separate **conversation history**, **curated memories**, **work objects**, and **reminders**. Retrieve a bounded set of relevant memories before an explicit Claude request; show the user what was recalled and where it came from. Keep writes deterministic and inspectable. A vector database, autonomous reflection agent, and framework migration are not prerequisites.

The useful patterns are Letta’s distinct context layers, Mem0’s scope protection and mutation history, and LangMem’s typed records with runtime namespaces. Worklane should retain its own permission model: remembering a preference does not authorize changing Jira, posting a GitLab comment, or sending a message.

## Concrete Worklane design

The following is a **recommended application contract**, not an imported upstream implementation or a statement that every field has already shipped.

1. **Conversation record:** account scope, work-object identity, message ID, role, text and timestamp. Reloading the Electron renderer should restore completed exchanges and drafts. A pending request is identified separately; reopening a panel must not automatically repeat it.
2. **Memory record:** stable ID, authorized account scope, optional object scope, kind (`preference`, `decision`, `constraint`, `follow_up`), text, source (`user_explicit` or `assistant_suggested`), source message/object IDs, confirmation state, revision and timestamps. Do not store API tokens, credentials or raw settings in memory content.
3. **Recall:** select the current account first; prioritize exact object/key matches and confirmed user preferences; then keyword matches. Cap count and combined text length. Return the selected record IDs with the answer context so the UI can show “Using 3 memories” and let the user inspect or forget one. These ranking choices are Worklane recommendations, not a benchmark result.
4. **Correction:** “Actually, use three attempts” updates the intended record only after an unambiguous target is selected. Preserve a revision/provenance trail according to the product’s retention policy. Competing inferred facts should be candidates, not silent overwrites.
5. **Forget:** remove a record from recall immediately; clear relevant retrieval caches; invalidate in-flight extraction/update work using a scope/revision generation. If the user asks to erase retained content, also purge text-bearing history and summaries or disclose what remains. Retained transcripts must not automatically reconstruct a forgotten memory. A scope reset must fence late responses from the previous account.
6. **Reminders:** store explicit `dueAt`, timezone, source object, status and last delivery/dismissal identity separately. Use deterministic due-time checks, deduplication, snooze and complete actions. On reopen, reconcile overdue reminders. If delivery only runs while the app is open, state that clearly; do not promise closed-app delivery before an OS/background mechanism exists.
7. **Quiet presentation:** Home Brief shows a few actionable pending items; the side assistant recalls context on demand. The robot represents `idle`, `thinking`, or `talking`; it does not imply the assistant continuously monitors external systems or that it has completed an action.

### Acceptance gates for the implementation

- Restart the app: confirmed memory and completed conversation survive; no Claude call happens merely because the panel reopened.
- Same hostname, different credentials/account: old memories and conversation are not sent under the new identity.
- Change MR file/line: keep the MR conversation, while the evidence in the next request reflects the current selection.
- Switch issue/document/MR: object-specific conversations stay separate; intentionally account-wide preferences may still be recalled with their source visible.
- Correct or forget during a delayed request: its late result cannot resurrect deleted content or override the newer revision.
- Provider failure: distinguish unavailable recall/extraction from “nothing remembered”; retain user input and allow explicit retry.
- Reminder due during restart/sleep: produce one overdue item, not repeated duplicate notifications; do not mark delivery complete before it occurred.
- Every external mutation still requires the user’s instruction/confirmation, independently of what memory suggests.

## Meta Muse: product and interaction reference

Reviewed Meta’s September 2026 primary product/design/security publications on October 4, 2026. This is a product-pattern review, **not a Muse source-code audit or verification of its operational claims**. The general [Muse landing page](https://ai.meta.com/muse/) exposed no readable design detail to the research tool; the following claims come from its linked first-party articles.

The [design article](https://introducing.muse.ai/) describes a long-running main conversation, optional side chats, an avatar with current-work status and access to activity/approved permissions, editable memory files, and structured approval cards. It also explains that proactive messages should earn their interruption and that some outputs belong in interactive artifacts instead of a long chat response. These are useful interaction patterns; they do not require copying Meta’s visual identity.

The [security article](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse) describes a separate enforcement component for external actions, narrowly scoped approvals outside the model conversation, isolated credentials, and inspectable memory/files. The [product announcement](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/amp/) describes persistent memory, a dedicated cloud computer, activity transparency, and user control over access. Those are Meta’s descriptions, not capabilities inferred for Worklane.

### Concrete Worklane adaptation

- **A persistent assistant space:** allow an optional dedicated window as well as the compact side panel. Preserve the same conversation identity and draft when changing presentation. Keep a visible object chip such as “Discussing PAY-382”; opening another issue must not silently redirect an in-progress action. Give an intentional way to start a separate topic.
- **Inspectable memory:** show recalled records with their source and edit/forget controls. Distinguish a user-confirmed preference from an assistant suggestion, and distinguish the conversation transcript from durable memory. A friendly robot can convey idle/thinking/replying without pretending to be a person or an always-running worker.
- **Action provenance:** pair each proposed action with its target, meaningful changes, explicit confirm/cancel controls, and a success/failure receipt backed by the adapter result. Enforce permissions in application code outside generated text. Never place integration credentials in chat or memory.
- **Quiet continuity:** keep pending follow-ups in the Brief and show meaningful progress in the assistant’s activity view. Reconcile overdue reminders when Worklane reopens. Until an independently tested OS/background runtime exists, state “while Worklane is open”; a separate window alone does not provide Muse’s dedicated cloud VM or closed-app execution.

These are proposed application decisions informed by the sources, not imported Muse implementation or claims of feature parity.
